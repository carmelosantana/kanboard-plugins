# Pick PixiJS and GSAP for the track

Use **PixiJS 8.22 with GSAP 3.15** for the race-track view. Pixi has the fastest 2D path of any engine reviewed. It runs on both WebGL and WebGPU, has the right building blocks for a road and a crowd (`MeshRope` or a custom mesh strip for the road, `ParticleContainer` for spectators), and ships one vendorable file of about **237 KB gzipped**. GSAP covers the easing, timelines and motion paths that Pixi does not have. The runner-up is **Phaser 4.2.1**. It is heavier (320–353 KB gz) and WebGL 1 only, but it comes with splines, arc-length paths, a `PathFollower` and a full tween manager, and it is almost CSP-clean. The popular 2D engines that actually shipped built-in 3D in 2026 are **melonJS** (3D meshes in v19 in April, then a full WebGPU 2D+3D renderer with glTF, lights and instancing in v20 in August) and **LittleJS** (a 21 KB built-in "LittleJS 3D" renderer in v1.19.3, 22 September). Phaser 4 explicitly stays 2D. Its 3D lives in a closed, AI-agent-only product called Phaser AE. Neither melonJS nor LittleJS is the right base here. Their 3D is weeks to months old, they release several times a week with breaking changes, and the project needs almost no 3D. The one integration risk with Pixi is Kanboard's own CSP: the core default is `default-src 'self'` with no `blob:` and no `unsafe-eval`. Pixi's blob workers and eval-generated code paths must be handled with flags and its shim, not by widening a policy that applies to the whole app.

## melonJS and LittleJS shipped real 3D, but Phaser's is a different product

The question's "2D engine that recently got 3D" fits **melonJS** best. Version 18 (March 2026) was a TypeScript modernisation with no 3D. **v19.0.0 (14 Apr 2026)** added a `Mesh` class, OBJ/MTL loading, `drawMesh()` on both the WebGL and Canvas renderers, and perspective matrices. **v20.0.0 (21 Aug 2026)** then added a WebGPU renderer "covering the entire engine feature set, 2D and 3D", with automatic fallback from WebGPU to WebGL 2 to Canvas. It also brought glTF scenes, `Camera3d`, `Sprite3d` billboards, point and spot lights (up to 32), and an `InstancedMesh` demo of a "100 000-tree forest" running at 60 fps ([melonJS 19.0.0](https://github.com/melonjs/melonJS/releases/tag/19.0.0), [melonJS 20.0.0](https://github.com/melonjs/melonJS/releases/tag/20.0.0)). The project now calls itself a "2.5D game engine" of about **250 KB minzipped**. It uses blob shadows and "deliberately not shadow mapping", which tells you the target is stylised 2.5D, not general 3D ([melonJS README](https://github.com/melonjs/melonJS/blob/master/README.md)). The cost is churn. There were 13 releases between 20.0.0 and 20.10.1 in two months, several breaking changes across v19 and v20 (start-up became `new Application()` plus `await app.init()`), and the revival followed a 21-month dormancy ([melonJS releases](https://github.com/melonjs/melonJS/releases)).

**LittleJS** came second and is moving faster still. It first added a Three.js bridge plugin (v1.18.26, Aug 2026). Then **v1.19.3 (22 Sep 2026)** added built-in, zero-dependency 3D of about **21 KB gzipped**. It draws into the same WebGL canvas as the 2D sprites, with primitives, OBJ loading, sun shadow maps, fog, heightmap terrain and instanced drawing ([LittleJS v1.19.3](https://github.com/KilledByAPixel/LittleJS/releases/tag/v1.19.3)). Within a month it gained glTF skinning, SSAO, water, environment maps and a 3D level editor (v1.20 to v1.28). It remains WebGL-only, and skinned animation runs on the CPU ([LittleJS releases](https://github.com/KilledByAPixel/LittleJS/releases)). The release notes of both projects read as heavily AI-assisted. That is an inference from their cadence and auto-generated text, but it reinforces the advice to pin a version and wait for the API to settle.

**Phaser** did not add 3D. Its July 2026 post, titled "No, you didn't miss a 3D update", says Phaser 4 "is going to stay a 2D engine". The 3D, WebGPU-first "Phaser AE" is closed source, has no public API for humans, and can be used only through the paid Phaser Game Agent or its MCP server ([Phaser 4 vs Phaser AE](https://phaser.io/news/2026/07/no-you-didn-t-miss-a-3d-update)). The 4.2 `Mesh2D` is, in the release notes' words, "not for 3D models" ([Phaser v4.2.0](https://phaser.io/news/2026/06/phaser-v4-2-0-released)). **PixiJS has no official 3D.** It offers a shared WebGL context with Three.js (v8.7). The community Pixi3D package stopped at Pixi v7 ([PixiJS blog](https://pixijs.com/blog), [npm pixi3d](https://www.npmjs.com/package/pixi3d)).

Two size gotchas affect a vendored setup. Three's `three.module.min.js` imports `./three.core.js`, not the minified core. Loading it as published pulls in about 376 KB gz, unless you vendor `three.core.min.js` under the unminified file's name. Babylon's npm `babylon.js` is byte-identical to `babylon.max.js`, so its only single-file build is effectively unminified ([three.module.min.js](https://cdn.jsdelivr.net/npm/three@0.186.1/build/three.module.min.js), [Babylon CDN](https://cdn.babylonjs.com/babylon.js), [Babylon ES6 docs](https://doc.babylonjs.com/setup/frameworkPackages/es6Support)). Motion has no self-contained ESM file. Its `+esm` route is a CDN-generated module chain that jsDelivr says must not be used with SRI, so vendor the UMD `dist/motion.js` instead ([Motion quick start](https://motion.dev/docs/quick-start), [jsDelivr +esm](https://cdn.jsdelivr.net/npm/motion@14.5.0/+esm)). On licensing, everything is permissive except GSAP. GSAP is free for commercial use under Webflow's proprietary Standard licence, which Webflow can revoke and which forbids use in no-code animation builders that compete with Webflow. A Kanboard plugin is not such a builder ([ScanCode LicenseDB](https://scancode-licensedb.aboutcode.org/gsap-standard-no-charge-2025.html), [npm gsap](https://registry.npmjs.org/gsap/latest)). Swap in Motion if the plugin has to stay OSI-pure.

## Kanboard's default CSP is the real constraint, not bundle size

A check of the local Kanboard 1.2.47 source shows the default `cspRules` are `default-src 'self'; style-src 'self' 'unsafe-inline'; img-src * data:`, applied to every response by `BootstrapMiddleware` (`kanboard-1.2.47/app/ServiceProvider/ClassProvider.php`, lines 187–191). With no `script-src` or `worker-src`, both fall back to `'self'`. That rules out CDN scripts, `eval`/`new Function`, `blob:` workers and wasm. It makes vendoring the files into the plugin's `Assets/` mandatory, not just tidier. A plugin can change this with `setContentSecurityPolicy()`, but that method **replaces the global rules for the whole application** (`app/Core/Plugin/Base.php`, line 26). A visualisation plugin should not do that, and the suite's existing tests already enforce CSP-safe templates with no inline scripts (for example `TimeReport/Test/TemplateAssetsTest.php`).

Under that policy, Kaplay, GSAP, Motion's UMD and Three's core bundle are clean. Phaser's single `new Function` is a webpack `globalThis` fallback that modern browsers never reach, so **Phaser runs untouched**. Excalibur only feature-detects. **Pixi needs care**. It spawns four inline workers via `new Worker(URL.createObjectURL(new Blob(...)))`, and it contains a try/catch probe for `new Function`. It also publishes a 15.7 KB `unsafe-eval.min.js` shim that replaces the eval-generated paths with static code ([pixi.min.mjs](https://cdn.jsdelivr.net/npm/pixi.js@8.22.0/dist/pixi.min.mjs), [unsafe-eval.min.js](https://cdn.jsdelivr.net/npm/pixi.js@8.22.0/dist/packages/unsafe-eval.min.js)). The notes did not confirm which Pixi features fail without the shim, or whether the blob workers have a main-thread fallback. The known remedies are loading the shim and turning off worker-based asset loading. The `preferWorkers` asset preference is from model knowledge, not a cited source. Prove both in a 30-minute spike before you commit. PlayCanvas and Babylon need `blob:` workers and `'wasm-unsafe-eval'` as soon as you touch compressed assets, physics or WebGPU, which disqualifies both on CSP alone.

## Build the track as a centripetal spline extruded into a mesh strip

Track rendering does not depend on the engine. The established procedural pipeline is: scatter 10–20 random points, take their convex hull, push close vertices apart, insert randomly displaced midpoints for concavity, cap the angle between segments at about 100°, then fit a closed Catmull-Rom spline. Extrude it by offsetting each sample ±halfWidth along the normal ([Game Developer](https://www.gamedeveloper.com/programming/generating-procedural-racetracks)). Use **centripetal** parameterisation (α = 0.5), because it avoids the cusps and self-intersections the uniform variant produces ([Wikipedia](https://en.wikipedia.org/wiki/Centripetal_Catmull%E2%80%93Rom_spline)). Sample by **arc length**, not by the spline parameter t, or quads bunch up in corners. Compute signed curvature κ = (x′y″ − y′x″)/(x′² + y′²)^{3/2} at each sample. A smoothed |κ| with hysteresis separates straights from turns, and the sign of κ picks the inside edge for red-and-white curbs. Curb placement is standard differential geometry; no source prescribes thresholds. If the plugin builds tracks from discrete segment records, a turtle walk (advance a length, turn an angle) produces the control points directly.

In Pixi, push the arc-length samples into a `MeshRope` with a repeating asphalt texture (`textureScale > 0`), or build the left/right strip yourself as `MeshSimple` vertices for full UV control ([PixiJS mesh guide](https://pixijs.com/8.x/guides/components/scene-objects/mesh)). Put the spectators in one `ParticleContainer` fed from a single atlas, with only position marked dynamic. Pixi's author measured 1M particles at 60 fps against 200K plain sprites, with movement logic, not rendering, as the bottleneck. The API is still labelled experimental ([ParticleContainer v8](https://pixijs.com/blog/particlecontainer-v8), [ParticleContainer guide](https://pixijs.com/8.x/guides/components/scene-objects/particle-container)). A periodic y-offset or tint change on a subset gives a convincing crowd "wave". For cars, keep a normalised arc-length u per car. Ease u with GSAP for scripted moves, or integrate u from a speed profile v(s) that slows where |κ| is high. Either way, read position and heading from your own arc-length lookup table. Phaser gives you the same thing out of the box: `Path.getPoint` is already arc-length based, and `startFollow({ease, rotateToPath})` drives a follower with one tween. That single tween is also its limit, because varying the ease along the path means dropping back to a hand-driven sprite ([Phaser curves-and-paths SKILL.md](https://unpkg.com/phaser@4.2.1/skills/curves-and-paths/SKILL.md), [Phaser Discourse](https://phaser.discourse.group/t/path-follower-using-a-timeline/9018)). To regenerate a track smoothly, resample both centrelines to the same N points. For closed loops, align them by testing every cyclic shift and both windings, then lerp with an eased t and rebuild the strip each frame. When a segment changes length or angle, interpolating the segment parameters instead avoids "inside-out" folding ([Cavalry Morph](https://cavalry.studio/docs/nodes/behaviours/morph/)).

## Conclusion

The engines that recently added 3D are the wrong choice for this brief, for the very reason they made news. melonJS and LittleJS are each re-founding themselves around 3D at a pace that breaks APIs monthly, and the brief needs a stable 2D surface. **PixiJS + GSAP** gives the best 2D throughput, a WebGPU path, and the exact primitives for a road strip and a crowd, at the cost of one CSP spike. Choose **Phaser 4** instead if that spike fails or if you value built-in path followers over raw speed. Accept that Phaser's open-source releases have been quiet since July while the company focuses on its closed AE. Plain Canvas2D with GSAP stays a sound fallback for a lightweight board widget with a few hundred objects.

The decision that lasts longer than the engine choice is to keep the track model engine-agnostic: centripetal spline, arc-length table, curvature profile, per-car u. Then a later move to 3D, with Three.js as the lightest mature option once its core-filename gotcha is handled, changes only the renderer, not the simulation. Still unverified: neutral 2026 cross-engine benchmarks (every figure here is self-reported), Pixi's exact behaviour with no blob workers and no eval, and whether melonJS's 3D API has stabilised.
