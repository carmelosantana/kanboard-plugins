# Keep Kanboard authoritative, borrow git's plumbing

Researched 2026-11-17 for Kanboard v1.2.47 on Docker/Dokploy. Built from five research notes (Forgejo/Gitea, CI runners, identity and credentials, lightweight SSH servers, Rust options), the sibling report `docs/research/2026-11-17-kanboard-orgs-sso.md`, and the side-session note on SSO for git.

The recommended default is a **Forgejo 15 LTS sidecar treated as a headless git engine**. A new Kanboard suite plugin owns the repo↔project mapping. It pushes project membership into Forgejo teams through the admin API, runs a reconcile job to catch drift, and gives agents short-lived, repo-scoped tokens. CI runs on **ephemeral Forgejo Runners on a gVisor runtime**, kept off the Docker daemon that runs Kanboard. The one serious challenger is a **thin gateway**: stock sshd with `AuthorizedKeysCommand` and a forced command, plus nginx `auth_request` in front of `git http-backend`. In that design Kanboard answers every access check live, so access always matches project membership, but you get no pull-request UI, no branch protection and no off-the-shelf CI. Everything else falls away. Soft Serve was archived in October 2026 and gets no more security fixes. Radicle's private-repo transport was disclosed as unencrypted. Every Rust forge is weeks old. gitoxide still cannot serve pushes. Two constraints drive the design. First, Kanboard cannot act as an identity provider. Second, AI agents never do an interactive login, so any setup that syncs groups at login leaves agents with stale access. Kanboard has to push or answer access decisions itself. Performance hardly separates the candidates, because every serious option runs C git for the pack protocol. What differs is where the access check runs and how much sits idle in memory, and those are what the prototypes should measure.

## Agents never log in, so Kanboard must push access or answer it live

Kanboard only consumes identity. Core supports LDAP and reverse-proxy headers, and the generic `plugin-oauth2` adds an OAuth2/OIDC client. Searches found **no plugin that turns Kanboard into an OAuth2/OIDC provider** ([plugin-oauth2](https://www.github.com/kanboard/plugin-oauth2)). Forgejo therefore cannot sign users in "with Kanboard". Humans can share SSO only through an external IdP such as Authentik, which the sibling report already recommends for Kanboard login. Kanboard also has no organisation entity. **Groups are the unit**: they are flat, and they reach projects through `project_has_groups`. The OAuth2 plugin turns IdP groups into Kanboard groups (`external_id` = group name) and re-syncs them **only at login**. For humans, the stable key that joins Kanboard to other systems is the IdP `sub`, stored in `users.oauth2_user_id`. The Kanboard username is not stable.

Agents are a separate population. They call `/jsonrpc.php` with HTTP Basic auth, using their username and a personal API token, and their permissions follow that user ([Kanboard API authentication](https://docs.kanboard.org/v1/api/authentication/)). Nothing indicates these tokens can be scoped or expire. An agent never visits an IdP, so it has no `sub`. The git layer should key its users on the **Kanboard `user_id`**, which every user has. It can also store `oauth2_user_id` for humans, so a later SSO login links to the same forge account.

That rules out the obvious IdP shortcut. Forgejo can map OIDC group claims to org teams, with optional removal ([Forgejo OIDC group mappings](https://forgejo.org/docs/latest/admin/advanced/oidc-group-mappings/)), but the documented Gitea flow applies that mapping when the user logs in ([Gitea blog](https://blog.gitea.com/feature-preview-mapping-oidc-groups-to-teams)). An agent that only pushes with a token would keep whatever access it had last. The SSO path also doesn't fit the data model, because access is granted per Kanboard project, not per IdP group. Mirroring project roles into IdP groups adds a hop and still leaves agents stale. Gitea and Forgejo have **no per-request external authz callback**, and no SCIM server was found. Two designs survive. Either Kanboard pushes membership changes into the git host and then reconciles, or the git host asks Kanboard on every connection. Each prototype below tests one of them.

Group grants add a complication. A user can reach a project through `project_has_groups`, and the OAuth2 plugin changes group membership during login without firing a project-membership event. Any push-sync design therefore needs a periodic **reconcile job**. That job expands each project's direct and group members, diffs them against the forge teams, and removes anything Kanboard does not grant. The forge teams count as "managed", so manual edits get overwritten. Without the reconcile job, push sync drifts every time an event is missed or the forge is down.

## Forgejo 15 LTS already has the API surface an agent-first plugin needs

Forgejo is a single Go binary, **GPLv3+ since v9** ([Forgejo GPL post](https://forgejo.org/2024-08-gpl/)), and is community-governed. A new major ships every three months. **v15.0 is the LTS until 15 July 2027**, v17.0 is current, and v19.0 (April 2027) is the next LTS ([Forgejo v17.0 release](https://forgejo.org/2026-10-release-v17-0/)). Running an unmodified copy as a sidecar triggers no copyleft obligations, because GPLv3 is not AGPL. That is my reading, not legal advice. Gitea is the MIT alternative, steered by the for-profit Gitea Ltd. **Gitea 28.0** (30 Sep 2026) added first-class **bot accounts**: token-only, no interactive login, no notifications. It also added a built-in audit log and repo-scoped deploy tokens ([linuxiac Gitea 28.0](https://linuxiac.com/gitea-28-0-drops-1-x-versioning-adds-audit-logs-and-bot-accounts/)). That is the closest built-in match for "API-only agent users". The two codebases have diverged far enough that clients must be written against each forge's own swagger. Forgejo still advertises Gitea 1.22 compatibility ([Codeberg swagger](https://codeberg.org/swagger.v1.json)).

Forgejo still wins on one feature that matters most for agents. **Forgejo 15 can restrict an access token to a specific list of repositories** ([Forgejo v15.0 release](https://forgejo.org/2026-04-release-v15-0)). Such tokens carry only `read/write:repository` and `read/write:issue` and cannot perform administrative operations ([Forgejo token scope](https://forgejo.org/docs/v15.0/user/token-scope/)). No equivalent was found in mainline Gitea, where scopes restrict groups of API routes, not specific repos. The provisioning endpoints are all present in Forgejo 17's live spec: `POST /admin/users`, admin-created orgs, admin-added SSH keys, **admin-issued user tokens** (`/admin/users/{username}/tokens`, so no user password is needed), collaborators, repo and system webhooks, and org Actions secrets ([Codeberg swagger](https://codeberg.org/swagger.v1.json)). A `Sudo:` header lets one admin token act as any user ([Forgejo API usage](https://forgejo.org/docs/latest/user/api-usage/)). The team-membership endpoints are long-standing, but they did not appear in the parts of the spec that were read. Confirm them against `/swagger.v1.json` before the prototype depends on them.

Because each repo belongs to exactly one project, the cleanest mapping is **one Forgejo org per Kanboard project**. Teams map to Kanboard roles: Manager = admin, Member = write, Viewer = read. Repos live under that org. This keeps URLs readable (`kb-<identifier>/<repo>`), and runners and Actions secrets can then be scoped to the project. It also turns "move a repo to another project" into a Forgejo repo transfer, which is cheap and rare. The plugin stores `(repo_id, project_id)` in its own table, so Kanboard remains the source of truth for the mapping. For agents, the plugin adds a JSON-RPC method such as `getGitCredential(task_id)`. The method authenticates the agent with its own Kanboard token, checks that it belongs to the task's project, and mints a repo-specific PAT for that project's repos. A `git credential-kanboard` helper calls it on `get` and returns `password_expiry_utc`, so git fetches a new token once the old one expires ([gitcredentials](https://git-scm.com/docs/gitcredentials)). One part is unverified: whether a repo-scoped token can be created for another user, with an expiry, through the admin API. If it can't, the plugin enforces the TTL itself by deleting tokens on a schedule. Protected branches cover the "agents never push to main" rule. Restrict pushes to a maintainers team that excludes agent accounts, require approvals from that team, require status checks, and protect workflow files so an agent cannot rewrite CI to extract secrets ([Gitea protected branches](https://docs.gitea.com/usage/access-control/protected-branches)).

Humans get a real code-review UI on a sibling subdomain. Serving Forgejo under a sub-path of Kanboard's domain works, but Forgejo's docs say it "offers no protection" against the resulting same-origin risk ([Forgejo reverse proxy](https://forgejo.org/docs/latest/admin/setup/reverse-proxy/)). Deep links from Kanboard tasks beat iframes. For human SSO, Authentik can sit in front of both apps. Forgejo's OAuth2 *provider* tokens have **no scopes** ([Forgejo OAuth2 provider](https://forgejo.org/docs/latest/user/oauth2-provider/)), so Kanboard should never get its powers through "Login with Forgejo".

On ops weight, Forgejo is one container plus a database. No vendor publishes a RAM floor. Community reports range from "comfortably" on 512 MB with Postgres on a Pi 4 ([DEV](https://dev.to/selfhostingsh/forgejo-vs-gitlab-ce-8a1)) to 1–2 GB for 10–30 users ([DEV](https://dev.to/royce_fabbd83cb268312e928/gitea-vs-forgejo-vs-gitlab-self-hosted-2026-2pc9)). SQLite serializes writes, so use Postgres if many agents will push and comment at once. Budget for monthly patching. Gitea 1.27 alone fixed 45 CVEs ([linuxiac](https://linuxiac.com/gitea-1-27-released-with-actions-improvements-and-45-cve-fixes/)), and Forgejo tracks a similar codebase.

## A few hundred lines of gateway make Kanboard the live authority

The alternative copies the pattern GitLab, Gitea and sourcehut all use, and drops the forge. OpenSSH's `AuthorizedKeysCommand` runs a program that looks up the offered key and prints an `authorized_keys` line with a forced command ([sshd_config](https://man.openbsd.org/sshd_config)). The forced command reads `SSH_ORIGINAL_COMMAND`, asks Kanboard whether this key's user may read or write repo X, and then `exec`s `git-upload-pack` or `git-receive-pack`. GitLab does exactly this through `/internal/api/allowed` and re-authorizes pushes in pre-receive ([GitLab Shell](https://docs.gitlab.com/development/gitlab_shell/)). sourcehut does it with `gitsrht-dispatch` ([man.sr.ht](https://man.sr.ht/git.sr.ht/installation.md)). Over HTTP, nginx `auth_request` sends one small subrequest to a Kanboard endpoint, sets `REMOTE_USER`, and hands the pack stream to `git http-backend` through fcgiwrap. git-http-backend enables push only when `REMOTE_USER` is set ([git-http-backend](https://git-scm.com/docs/git-http-backend)). PHP never touches the pack bytes, which avoids FPM timeouts and buffering problems on large clones. Pass `GIT_PROTOCOL` through, with `AcceptEnv` on SSH and the header over HTTP, so clients get protocol v2's smaller ref advertisement ([gitprotocol-v2](https://git-scm.com/docs/gitprotocol-v2)).

The appeal is **revocation lag of zero**. Remove someone from a Kanboard project, and their next fetch is denied because nothing was copied anywhere. Agents can push over HTTP with tokens. Those should be git-only tokens minted by the plugin, not the agent's unscoped Kanboard API token, which would hand the whole JSON-RPC surface to anyone who reads a git remote URL. For short-lived SSH, use a Kanboard-held CA that signs certificates via `TrustedUserCAKeys`. `AuthorizedPrincipalsCommand` can then map principal and key ID to a user and a task ([sshd_config](https://man.openbsd.org/sshd_config#AuthorizedPrincipalsCommand)). The idle footprint is sshd, nginx and git, with no daemon of its own. For browsing, **cgit is maintained again**, with 1.3 in February 2026 as its first release in six years ([cgit 1.3](https://lists.zx2c4.com/pipermail/cgit/2026-February/004968.html)), and it can sit behind the same `auth_request`.

The costs are real. The access check now sits on the hot path. It runs on every connection and every offered key, so it has to be a direct indexed database lookup, not a full Kanboard HTTP bootstrap. That couples git availability to Kanboard's database. Branch protection, pull requests, review and webhooks all become plugin work: a pre-receive hook for "never main", a post-receive hook that notifies Kanboard, and any diff/review UI inside Kanboard. The human-facing UI is secondary but not optional. A gateway that cannot show a reviewer a diff pushes that work onto Kanboard templates. **gitolite** is the off-the-shelf variant of this design. It is GPL-2.0 and still maintained (v3.6.15, August 2026), now pointing at Codeberg. Kanboard can either write a generated `gitolite.conf` and run `gitolite compile`, or supply live groups through `GROUPLIST_PGM` ([gitolite conf](https://gitolite.com/gitolite/conf.html#getting-user-group-info-from-ldap)). `gitolite access -q` answers access queries ([gitolite access](https://github.com/sitaramc/gitolite/blob/master/src/commands/access)). It saves you from writing the access engine but brings back a compile step. For a single-owner mapping (one repo, one project, three roles), the custom shim is likely smaller than learning gitolite's rule language.

## Soft Serve, Radicle and the Rust forges fail on maintenance or security

**Soft Serve is gone.** Charm archived it on 2026-10-26 after v0.12.4, saying "No further security updates will be applied" ([soft-serve README](https://github.com/charmbracelet/soft-serve)). Its 2026 history includes an authentication bypass, a privilege escalation to global admin, and leaks of private repos to `no-access` collaborators ([soft-serve releases](https://github.com/charmbracelet/soft-serve/releases)). It also kept access rules in its own database, with no external hook. Choosing it now means maintaining a Go fork. **Radicle** (MIT/Apache-2.0, 1.10.3) uses delegates and cryptographic identities, not team membership. In September 2026 it disclosed that node-to-node traffic was unencrypted and that Node IDs could be impersonated to fetch private repos. The fix is a breaking move to iroh ([InfoQ](https://www.infoq.com/news/2026/09/radicle-network-vulnerabilities/)). At most it could serve as a publish mirror for public repos.

The Rust picture splits in two. The building blocks are mature: **russh** has 100+ contributors and about 4.8M recent downloads ([russh](https://github.com/warp-tech/russh)), and axum is widely used. Server-side git is not. gitoxide's own status file still lists push, upload-pack/receive-pack server plumbing, and a general server `accept()` as unchecked ([crate-status.md](https://github.com/GitoxideLabs/gitoxide/blob/main/crate-status.md)). It is also pre-1.0 and ships a breaking release roughly every two weeks. Every Rust forge found is hobby-scale. Forgust, IronForge, forgente and omaforge have 0–4 stars each and 1–2 contributors, and Forgust is five days old ([Forgust](https://github.com/forgust-dev/forgust), [IronForge](https://github.com/lengyuqu/ironforge), [forgente](https://github.com/yamz8/forgente)). GitHub's Spokes and GitLab's Gitaly took big teams years to build, and both still run C git for the pack protocol ([GitHub DGit](https://github.blog/engineering/architecture-optimization/introducing-dgit/), [Gitaly 1.0](https://about.gitlab.com/blog/the-road-to-gitaly-1-0/)). Git 3.0 plans SHA-256 and reftable defaults for April 2027 ([LWN](https://lwn.net/Articles/1094575/)). Any git implementation other than C git risks lagging behind that change, and shelling out to `git` avoids the risk.

There is one Rust option worth keeping: a **thin Rust gateway** that uses russh for SSH and axum for HTTP, and spawns real `git upload-pack`/`receive-pack` after an in-process access check against Kanboard's database. It is the gateway design above shipped as one static binary, with metrics, rate limits and per-agent ref leases built in. It would not make git transfers faster. Its only performance gain is a cheaper access check than forking a process per connection, so it is justified only if prototype 2 shows that check is the bottleneck.

## CI follows the git host; isolation matters more than runner choice

**Woodpecker** (Apache-2.0, 3.20.x) is the lighter CI: about **100 MB server + 30 MB agent idle**, with a clean bearer-token API for trigger, list, logs, cancel and **approve** ([Woodpecker README](https://github.com/woodpecker-ci/woodpecker), [Woodpecker API](https://woodpecker-ci.org/api)). It only attaches to a forge, though. It has built-in drivers for Forgejo, Gitea, GitHub, GitLab and Bitbucket, and supports others through an **experimental addon-forge** interface that "can change and break at any time". Radicle is the only known addon ([Woodpecker forges](https://woodpecker-ci.org/docs/administration/configuration/forges/overview)). **Forgejo Runner** (GPLv3+ since v11) is built into the Forgejo design. It runs GitHub-Actions-style YAML, registers offline with a shared secret (handy for a compose stack), and has supported **server-enforced ephemeral one-job mode** since v15 ([Forgejo runner registration](https://forgejo.org/docs/latest/admin/actions/registration/)). It exposes dispatch, rerun and job-log APIs, plus job-status webhooks in v17 ([Forgejo v17.0](https://forgejo.org/2026-10-release-v17-0/)). With a Forgejo sidecar, Forgejo Runner is the default choice: one less service, workflow files that agents already know from GitHub, and no second set of OAuth credentials. Woodpecker earns its place only if its human approval gate and smaller footprint outweigh running a second service with its own login against Forgejo. For the gateway, neither runner fits without a fake forge. The natural CI there is a post-receive hook that queues a job, a small worker that runs `docker run --runtime=runsc` on a fresh checkout, and results posted back to the Kanboard task. Laminar is a ready-made version of this "hook plus script" model ([LinuxLinks: Laminar](https://www.linuxlinks.com/laminar-lightweight-modular-continuous-integration-service/)).

Whichever runner you pick, how jobs are isolated matters more. Agent-written code is untrusted. Forgejo's own docs warn that the runner "performs remote code execution", that host mode has no isolation, and that LXC is not a security boundary ([Forgejo runner installation](https://forgejo.org/docs/latest/admin/actions/runner-installation/), [Forgejo Actions security](https://forgejo.org/docs/latest/admin/actions/security/)). The PyTorch and TensorFlow runner compromises came from **non-ephemeral** self-hosted runners that ran pull-request code with secrets in reach ([SecurityWeek](https://www.securityweek.com/new-class-of-ci-cd-attacks-could-have-led-to-pytorch-supply-chain-compromise/)). On a single Dokploy host, **gVisor** is the practical boundary. It plugs into Docker as a runtime, needs no KVM, and starts containers in about the same time as plain Docker. Benchmarks put both at roughly 0.4–0.7 s, against 1.9–4.6 s for Kata ([Edera / arXiv 2501.04580](https://arxiv.org/pdf/2501.04580), [computingforgeeks](https://computingforgeeks.com/gvisor-vs-kata-containers-vs-runc/)). Its overhead lands on syscall- and network-heavy work, not CPU-bound builds ([gVisor performance](https://gvisor.dev/docs/architecture_guide/performance/)). Pair it with a separate Docker daemon (never the host socket that Kanboard and Dokploy use), per-job networks with egress deny-by-default, CPU/memory/pids caps, a job timeout, and no secrets in agent-triggered jobs. For jobs lasting minutes, image pulls and dependency installs cost more than any runtime's start time, so build caching is the real performance lever.

## Prototype candidates

All three should run the same scripted scenario against the :8081 dev stack (never the production MCP). An agent user, holding only a Kanboard API token, picks up a task in project P. It gets a credential, clones P's repo, pushes `agent/<task>-x`, has CI run, gets a pass or fail result back on the task, and is refused a push to `main` and a clone of project Q's repo. Then a manager removes the agent from P, and the agent's next fetch must fail.

| # | Architecture | Must demonstrate |
|---|---|---|
| 1 | **Forgejo 15 LTS + `KanboardGit` plugin + ephemeral Forgejo Runner on gVisor.** Org per project, role teams, push sync on project/group events plus a cron reconcile, `getGitCredential` vending repo-scoped PATs, a system webhook posting push/job status to task comments, protected `main` and workflow files. | Repo-scoped token creation for another user via the admin API; reconcile repairs injected drift (forge down during a membership change, group change via SSO login); CI result lands on the task; optional sub-variant swapping in Woodpecker to compare footprint and approval flow. |
| 2 | **Thin gateway: sshd `AuthorizedKeysCommand` + forced-command shim, nginx `auth_request` → fcgiwrap → `git http-backend`, cgit, all checking Kanboard's DB live.** Pre-receive hook for branch rules, post-receive enqueues a `runsc` job and comments on the task. | Revocation is effectively instant; Kanboard DB-down behaviour (fail closed, clear error); access check stays cheap under concurrent agents; how much of review/PR/status UI has to be built in Kanboard. |
| 3 | **Rust gateway (russh + axum spawning C git) with in-process access checks.** Same contract and same hooks as #2. Build only if #2's numbers justify it. | Lower access-check latency and RAM than #2 under load; single-binary deploy on Dokploy; per-agent ref leases or rate limits that #2 struggles to express. |

Compare them on these metrics. Clone and push latency, p50 and p95, at 1, 10 and 50 concurrent agents, with a medium repo over both SSH and HTTP. Access-check latency on its own. Idle and loaded RAM for the whole stack, including the CI runner. CI cold start to first log line, and total job time with a warm cache. **Revocation lag**: time from removing a member in Kanboard to the git operation being denied. Drift found and repaired after injected failures. Lines of plugin, shim and config code, and setup steps from an empty Dokploy host. Number of agent tool calls to go from task to green CI. Patch burden, meaning upstream releases a year that require action.

## Conclusion

Neither the forge nor the CI is the hard part. Kanboard is a good source of truth and a poor identity provider, and its most important users never log in. That turns "attach git to Kanboard" into a question of how access decisions leave Kanboard. Push them into Forgejo and you get a complete, patched forge in exchange for revocation lag and a reconcile loop you must own. Answer them live from a gateway and you get exact, instant access in exchange for rebuilding review, branch rules and CI around a bare git server. Forgejo 15's repo-scoped tokens are the one upstream feature that makes the push model fit agents well. They let the plugin give each task a credential limited to its project's repos, which is the core of the "agents work tickets" model. So prototype 1 is the likely MVP, and prototype 2's real job is to measure what that revocation lag costs.

One finding is easy to miss. Git performance will not decide this. Every viable option, including the Rust ones, runs C git for the transfer itself, so differences show up only in the access check, idle memory and CI isolation. The decision really comes down to operational simplicity, revocation lag and the human review experience. For the human side, a sibling Forgejo subdomain behind Authentik, with Kanboard deep-linking into pull requests, beats any embedding approach and costs nothing extra in prototype 1.

## Decisions taken after this research (2026-11-17)

Grilled on the dev board's map (Git Hosting, Kanboard #817). These supersede the report where they differ:

- Prototype **P1 only**: Forgejo 15 LTS sidecar, a KanboardGit plugin, and a separate **broker** service that holds the Forgejo admin token and exposes narrow verbs (sync membership, mint scoped token, revoke, authz check). An in-plugin admin token is allowed only as a mutually exclusive deployment mode; broker down means git authz fails closed.
- **Authentik** owns human identity; agents are Kanboard-issued principals; Kanboard project membership is the authz authority.
- Revocation takes effect on the **next git operation**, so P1 needs a live authz path, not push-sync alone.
- Agents get **per-task, repo-scoped, ~1h tokens** and push only their own prefixed branches.
- Software factory, not human review of every PR: **risk-tiered autonomous merge**. CI green plus approval from a different reviewer agent merges; CI/workflow, auth, dependency, infra and branch-protection changes need a human; merge queue and auto-revert guard main.
- Agent-branch CI gets **no secrets**. Runner isolation is the experiment axis: separate VM + gVisor, same host rootless + gVisor, Firecracker/Kata if the VPS exposes KVM.
- One project per repo; same Dokploy VPS for the git server; humans use the Forgejo UI via SSO.
